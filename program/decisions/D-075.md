# D-075: adaptive suite and connected features

Status: accepted scope, 2026-10-09, from the owner-designated v3 plan. Implementation and visual acceptance remain pending.

## Decision

At login/handoff, one accessible customer tool opens through `/go/<scope>` when no explicit redirect was supplied. Two or more accessible tools open OrgTik Home. Explicitly visiting Home never triggers that redirect. SOS has no locale URL prefix (D-033). Staff applications are not counted as customer subscriptions.

Use one suite context and connector registry, derived from the existing selected workspace, lines, tool grants and seats. A connected feature has four customer-facing outcomes: available; target tool not subscribed (owner can add/trial, others can request); no assigned access/seat (request access); billing read-only (explanation and owner recovery action). Role denial, disabled connectors and unavailable data must retain their actual reason rather than being mislabelled as billing or seats. Both tools' current access and connector state are checked. No broken or unauthorized deep link is offered.

Provide `useSuite`, one rail adapter and `ConnectedFeature` in `@orgtik/ui`; keep application providers responsible for domain data. Connectors carry the source/target, transferred data, workspace on/off state and consequences of cancellation. Add/export/request actions remain mock prototype flows.

P3 compatibility refinement, 2026-10-10: the retained privacy-preserving absence calendar is a minimal consuming-tool projection. It requires the consuming tool's current assignment, both workspace subscriptions and an enabled connection; it does not require an HR seat or grant HR directory access. Guests, missing HR subscriptions and disabled connections receive an empty projection. Full HR record operations retain their HR-seat checks. This preserves the accepted leave/calendar regression contract while adding the v3 subscription/connection gate.

## Bounded exception to D-073

The read-only feasibility review in [v3-feasibility.md](../v3-feasibility.md) identifies the existing command allowlist as a constraint. P3 may add only a route/command adapter needed to make an approved UI flow work through the existing workspace boundary. It must reuse current principals, tool checks, operation receipts and snapshot commit/rollback; it cannot replace session, tenant, CAS or journal semantics. No implementation change to those internals is authorized by P0. Any broader exception must be documented before its code is written.

## Acceptance

J16–J18 cover standalone entry, add-tool, seat request and cancellation. J8/J14 must use owner-domain mock endpoints rather than the isolated presentation bridge. Prove permission, subscription, seat and billing messages independently; retain D-071/D-072 Files contracts.
