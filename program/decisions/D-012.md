## Decision (2026-09-30)

**The website reads CMS content live from the Website Manager's public API at runtime**, chosen by Yossef at the G0 review (the draft proposed a build-time snapshot). Publishing is instant; the website does not adopt `@orgtik/ui` in this phase.

What follows, so D-005 and D-013 (zero visual change) still hold:
- **First paint:** the site already shows its "Loading OrgTik…" fallback while a page's code loads. The content request joins that same wait, so once a page renders it renders exactly as today, and the parity harness captures it after load as before.
- **Outages:** a last-known-good copy of the published content ships with every deploy and is used when the API doesn't answer within a short timeout. A CMS outage never blanks the site.
- **Speed:** the public API serves published bundles per page and locale, cacheable at the edge, invalidated on publish.
- **SEO:** the prerendered heads (S3) are generated from the API at deploy and again on publish, so crawlers get real titles and metadata without running JavaScript.
- **Previews** use the same path with a preview token.
- **Slice changes:** S1 builds the content client, the adapters and the fallback copy instead of the snapshot pull; the adapters' parity tests are unchanged.

## Context

- The website (Vite, React, plain JS) hard-codes all its content, and its design must not change (D-000).
- It's served as static files.
- SEO needs real head tags per route.
- A runtime dependency on the CMS would add a failure mode and a loading state the design doesn't have.

## Options

| Option | For | Against |
|---|---|---|
| A. Fetch from the CMS at runtime | Instant publishing | Latency, a failure mode, and layout shift during load |
| **B. Build-time snapshot** (proposal) | The site stays static and fast; nothing new can fail at runtime | Publishing waits for a build (minutes) |
| C. Move to SSR or SSG | Real HTML per route | The site reads `window` for breakpoints, so server rendering would change the first paint |

## Proposal

- On publish, `content:pull` writes `src/content/snapshot/{locale}/*.json`, and the snapshot is committed.
- Adapters rebuild the exact data shapes the page code uses today, so no page render code changes.
- Modes: `snapshot` (production), `api` (local development), `preview` (editors).
- The website keeps its own CSS and doesn't use `@orgtik/ui` in this phase.

## Consequences

- Each adapter gets a parity test.
- Editors use preview mode to see changes before the build.
