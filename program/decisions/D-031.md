# D-031: The website baseline follows the website's `main`

| | |
|---|---|
| Status | **Accepted** (2026-09-30) |
| Decided by | Yossef ("we have modified the website design… update the local… modify the plan to adapt it") |

## Decision

The website's design keeps evolving on `main` while the program runs. The parity baseline (D-013) is therefore the **latest approved `main`**, not a frozen commit. The first move is from `30db536` (`pre-cms`) to `d76ee3b` (PR #26, department case studies).

Each time `main` moves, the **website drift protocol** runs before any Website Manager work continues:

1. **Update:** fetch, then fast-forward the local checkout. Never rebase or merge local work into the website repo.
2. **Discover:** run `tools/qa/discover.mjs`, which records new, removed or renamed routes and aliases.
3. **Capture:** run `capture.mjs --label <sha>` at 390, 768 and 1440.
4. **Diff:** run `diff.mjs --base <previous baseline> --head <sha>`. The report must match what the change says it touches. Anything outside that is flagged to the owner before it becomes the baseline.
5. **Map:** turn the change into content-model, extraction, token and glossary updates (see the amendment in `plan.md`). Record them as a dated amendment.
6. **Promote:** the new capture becomes the baseline. The Website Manager's zero-visual-change check compares against it from then on.

## Consequences

- S1 extraction works against the current baseline. A page extracted before a website change is re-extracted if the change touched it, and its parity test is re-run.
- Extraction is safest on pages that have stopped changing. The drift reports show which pages move most, and S1 orders its pages by that, most stable first.
- The `pre-cms` tag stays where it is, as the first baseline. Later baselines are named by commit (`d76ee3b`, …) in `audits/website/parity/`.
