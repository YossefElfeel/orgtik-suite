# D-032: Case studies are one shared brief plus one block set per department

| | |
|---|---|
| Status | **Accepted** (2026-09-30), following the website's own design (PR #26) |
| Decided by | Follows the website owner's design; recorded by the program |

## Decision

In the Website Manager, `caseStudy` is one entity with two parts:

1. **A shared brief, the same for every project.** Client, timeline, team, challenge, goal, our role, the headline result (`highlight`), and the three section headings and intros ("How we got there", "What we delivered", "The results"). The gallery (05) and "More work" (06) stay as they were.
2. **A department block set: a discriminated union on `department`.** Each department keeps its own presentation, exactly as the website draws it:

| Department | Format label | How we got there (approach) | What we delivered | Results |
|---|---|---|---|---|
| design | Design journal | steps: when, title, detail, outputs | palette (name + hex), typeface, weights, touchpoints (label + image) | metrics (value + label), shifts (from → to) |
| development | Build log | steps + a `log` line each | core, layers, modules (name + Phosphor icon), stack | gauges (label + 0–100), metrics |
| hosting | Runbook | steps (one output each) | components (name, detail, state) | chart (label, cutover index, points), metrics |
| digital-marketing | Performance report | a timeline in weeks: steps with start and end weeks | week (day, task, items) | kpis (before, after, change), monthly series with a baseline, funnel, channels |
| it-support | Service log | tickets: id, when, title, detail, outputs, state | priorities (level, name, when, target) | comparisons (before, after, unit) |

**How it works:**
- The format follows the department and isn't edited separately. Changing a project's department is an explicit action: the editor maps or drops the blocks that don't fit, and nothing is silently discarded.
- Figures and charts are `Provenance`-governed claims. They keep the website's visible "Sample figure" / "Figures in this section are samples" labels until an approver with `claims:approve` marks them as approved project results (the website's own rule, `AGENTS.md` 2026-09-30).
- Chart data is edited as small typed series: label/value rows, with a cutover or baseline marker. The editor shows a live preview in the department's style.

## Why

The website no longer has one P17 layout for every project (as `orgtik-website-ia.md` assumed). It has one brief and five presentations. A single generic "sections" editor would lose the structure the design depends on. Five separate entities would duplicate the brief, the SEO, the slugs and the listing.

## Consequences

- The IA document's P17 description is out of date for case studies. The Website Manager follows the website as it is now (D-031).
- S1 extraction is simpler here: `src/reference/case-studies.js` is already a data file, with 5 projects and every figure. The section headings and labels in `CaseStudy.jsx` become strings.
- The Website Manager needs two editor types it didn't plan: a **series editor** (chart points, funnel, channel mix, gauges) and a **palette editor** (name + hex swatches). Both are added to S4, which already holds the Work editors.
