# D-017: No tokens in URLs

| | |
|---|---|
| Status | **Accepted** (2026-10-01) |
| Owner | Dev team (backend), Claude (front-end) |
| Approver | Dev team |
| Needed by | Shell v1 (Wave 1) |
| Evidence still pending | Backend support for a one-time code exchange |

## Context

- The SoSBar launcher hands the bearer token to each app in the URL (`/auth?token=`). A URL ends up in browser history, server logs and referrer headers.
- The static scan found 15 places that put a token in a URL: sos 7, sales 3, chats 2, files 1, marketing 1, content 1.
- SOS's "Login as" also does it.
- The baseline sweep so far (SOS, Tasks, Files and Sales complete, plus 7 of HR's 31 routes) found no page that *keeps* the token after sign-in. The apps strip it, but only after it has already been in the address bar.

## Proposal

- The launcher sends a **short-lived, single-use code** in the URL. The app exchanges it for a session with a POST, and the code can't be replayed.
- Staff use **"View as"** (read-only, audited, with a permanent ribbon) instead of "Login as".
- Tokens never appear in URLs, logs or analytics. The audit kit's `token_in_url` check and the static scan both enforce this.

## Consequences

- The front end isolates the hand-off in one function, `buildScopeHref`, so the switch is a small change when the backend is ready.
- Until then, apps must strip the token immediately. The sweep checks this on every page.


## Decision (2026-10-01)

Accepted by Yossef: No tokens in URLs: every app takes SOS's one-time code in its wave (the endpoints are a contract for the backend); **and** "View as" (read-only, audited) replaces "Login as".
