## Context and options

The review found missing cross-app foundations. Keeping renewal, proration, limits, sessions, PDF and 2FA entirely in R4 would leave earlier journeys without their dependencies. Building live providers now would turn the prototype into a production-backend project. The approved direction is a persistent hosted mock with useful customer and staff journeys, delivered in parallel and held to senior UI/UX prototype quality.

## Decision

Retain **R0 → R1 → R2 → R3 → R4**. Lift the purchased-seat quantity contract and shared proration calculation into R0; lift renewal, failed-payment progression, retries, recovery, seat changes and necessary session revocation into R1; deliver usage/limits, invoice PDF, audit retrieval and functional mock 2FA before their dependent R3 surfaces. Reuse these foundations in R4.

Payments, mailbox delivery, analytics, AI responses, signatures, external social/accounting integrations and tax-ID/e-invoice examples are deterministic mock flows. Live providers, arbitrary binary uploads, live call media and regulatory submission remain deferred. The existing persistent mock is the prototype's backend boundary; this decision does not authorize a new production backend or provider stack.

The maintained roadmap is `program/plan-v2-execution.md`; `program/backlog/release-packages.csv` carries package dependencies, owners, runtime consumers, status and evidence. Preserve all 72 benchmark commitments, recording implemented behavior, simulated behavior and external deferral separately.

## Consequences and acceptance

- Gate R0 on corrected Linux authentication/artifact checks and hosted desktop/mobile shell acceptance. PR #4 remains an integration preview; extract changes after foundation/review ancestors land. Preserve prior work and existing resources.
- Each package has one PR and clear file ownership; the shared API/library/shell integration owner coordinates shared changes. Affected deployment selection and runtime consumer testing are separate. Serialize shared-preview verification; deploy at most two projects concurrently.
- Prototype acceptance requires persona task completion, honest saving/delivery feedback, useful empty/error/no-access/read-only states, existing `@orgtik/ui`, five locale catalogs, Arabic RTL, light/dark and responsive layouts. Preserve website visual identity.
- Test all 15 journeys on an isolated verification deployment. Production smoke checks preserve accounts and historical invoices and never reset business data or advance the shared clock.
- Record external deferrals visibly; a mock demo does not close a live-integration commitment. Public Arabic website launch remains deferred.
