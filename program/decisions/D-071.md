# D-071: pinned Files references with intersected current permissions

Status: accepted implementation choice for the approved R2/D-066 roadmap,2026-10-08; reviewed source and scoped local acceptance; PR18 sourcea35a9f0 merged main438c237 after CI37724544919 passed.

A shared reference contains only workspaceId, fileId and immutable versionId. Tasks and Chats retain those identifiers and resolve visible metadata from Files on each authorized read. Selecting, attaching and opening a record requires current access to both the consuming task/conversation and Files, including inherited record permissions. Linking never widens the file's audience. Permission loss exposes an unavailable state without a cached filename, preview or download capability. Content also requires the actual stored reference in its authorized consumer record.

Existing readable Files records can be referenced while Files is read-only if the consuming tool permits the write. No owner or global role bypasses tool assignment or record permissions. Versions remain pinned after metadata changes; guessed future versions and cross-workspace identifiers fail. Public share capabilities remain separate from signed internal references.

New workspaces remain empty until a member explicitly creates a record from the packaged sample catalog. Creation and consumer mutations use stable operation keys and atomic checkpoints; failed persistence returns failure and exact replay cannot duplicate records or messages. Arbitrary binary uploads and live media transport stay deferred. The initial package provides immutable version1; broader version editing and structured whiteboard commitments still require their own implementation and evidence.
