# D-033: SOS keeps its URLs; its language lives in a cookie

| | |
|---|---|
| Status | **Accepted** (2026-10-01) |
| Needs | Dev team |

## Context

The other apps carry the language in the path (`/ar/my-files`). SOS has no locale segment, and its URLs are part of the suite's contract:
- the launcher's Home tile points at them
- every app's "not allowed" redirect points at them
- the sign-in page's `?redirect=` points at them

VS-1 needed SOS's sign-in in 5 languages without breaking any of that.

## Proposal

For now, SOS reads the language from a `NEXT_LOCALE` cookie, then the browser's `Accept-Language`, then English. It uses next-intl without i18n routing (`somion-sos-frontend-main/i18n/`).
- **Signed out:** people choose on the sign-in page, and the choice is remembered for a year.
- **Signed in:** the launcher passes that language to every app's hand-off, so Files opens in it.

## Options

| Option | For | Against |
|---|---|---|
| **Cookie (proposed, shipped in VS-1)** | No URL changes. Reversible. SOS pages can be translated one by one. | A shared link doesn't carry the language, so the recipient sees their own. Search engines can't index SOS per language, which doesn't matter for an internal app. |
| `/[locale]` routes, as in the other apps | Consistent with the rest of the suite. | Every SOS route and every inbound link moves. The launcher and the "not allowed" redirects need 301s. Best done in wave 2 with the rest of SOS's i18n. |

## Later

When a person is signed in, their profile's language (`profile.language` in `/auth/me`) should win over the cookie, and changing it in the user menu should update both. That's wave 2, when the SOS dashboard gets the shell.


## Decision (2026-10-01)

Accepted by Yossef: SOS keeps its URLs; its language lives in a cookie (no `/[locale]` routes).
