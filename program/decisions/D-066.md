## Context and options

The hosted prototype needs Files references, versioning and a credible save/reopen whiteboard flow. Arbitrary uploads would require binary persistence and a broader backend. Packaged sample assets already provide useful preview/download coverage, but an HLS `.ts` segment failed artifact verification at the inspected readiness gate.

## Decision

Use **packaged sample assets only** for binary file content. Preserve their bytes through Git checkout, Linux builds, runtime copying, downloads and previews; HLS transport-stream `.ts` assets are binary media, not TypeScript source.

Persist workspace-scoped Files metadata, permissions, references, comments and versions in the existing mock journal. Prototype upload/replace/version flows select packaged sample assets and clearly describe that behavior. Arbitrary binary upload storage and live media ingestion remain deferred.

Persist whiteboards as **structured drawing state**, authorize them in their workspace, and expose the associated Files record with seeded previews. A seed preview is illustrative; reopening the board must restore the saved drawing. Tasks/Chats attachments reference Files records and authorize every access.

## Consequences and acceptance

- Fix byte-preservation/readiness failures before dependent releases. Verify Linux packaged artifacts and downloaded sample bytes, including HLS segments.
- Cover whiteboard save/reopen and Files record linkage, metadata/version/comment persistence across cold starts, and scoped permissions/reference failures.
- Preserve all Files/WM benchmark commitments with explicit prototype simulation or external deferral; do not mark arbitrary upload capability complete because its metadata UI works.
- “Saved in Files” copy appears only when the associated record and structured state actually persist; otherwise copy describes the current supported save behavior.
